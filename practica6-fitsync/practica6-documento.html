Práctica 6 — FitSync: sincronización de actividad física entre smartwatch y dispositivo móvil

Objetivo: implementar la comunicación entre un smartwatch (Wear OS) y un dispositivo móvil (Android) mediante la Wearable Data Layer (MessageClient) para transferir registros de actividad física simulados, validando la integridad de los datos y detectando duplicados en el receptor.

1. Modelo de datos (Actividad 1)

El registro se representa con la clase ActivityRecord, serializada en JSON (Gson) y transmitida por la ruta /activity:

data class ActivityRecord(
    val id: String,            // UUID único
    val timestamp: Long,       // epoch ms
    val heartRate: Int,        // bpm
    val steps: Int,
    val durationSeconds: Int
)

2. Envío desde el smartwatch (Actividad 2)

El botón "Registrar actividad" genera una medición simulada con identificador único (UUID.randomUUID()) y la envía al teléfono emparejado:

val record = ActivityRecord.generateSimulated()
val json = gson.toJson(record)
messageClient.sendMessage(peer.id, "/activity", json.toByteArray(Charsets.UTF_8))

El nodo destino se obtiene con Wearable.getNodeClient(this).getConnectedNodes() y se elige el nodo isNearby (el teléfono emparejado y encendido).

3. Recepción, validación y almacenamiento (Actividad 3)

El teléfono escucha la ruta literal /activity y aplica el pipeline: deserializar → validar → detectar duplicado → guardar:

val record = gson.fromJson(json, ActivityRecord::class.java)
val errors = ActivityRecord.validate(record)
if (errors.isNotEmpty()) return "INVÁLIDO: ${errors.joinToString(", ")}"
if (repository.contains(record.id)) return "DUPLICADO: ${record.id} ya existe"
repository.save(record)
return "REGISTRADO: ${record.id} (HR ${record.heartRate} bpm, ${record.steps} pasos)"

La persistencia usa SharedPreferences ("fitsync_records") con Gson, de modo que el historial sobrevive reinicios de la app.

4. Historial y conectividad (Actividad 4)

La pantalla de historial (HistoryActivity) lista los registros válidos guardados, en orden descendente por fecha.

Comportamiento de conectividad de DataClient: la Wearable Data Layer encola localmente los mensajes cuando el nodo destino no está disponible y los entrega al restablecerse el enlace por Bluetooth. Por ello el envío no requiere reintentos manuales; aun así, la app verifica getConnectedNodes() antes de enviar para dar retroalimentación inmediata. Si no hay nodo cercano, se muestra "Teléfono no conectado" y no se envía.

6. Conclusión

La integridad de los datos se garantiza en el extremo receptor: el teléfono deserializa, valida contra reglas de plausibilidad (frecuencia cardíaca 30–220 bpm, pasos y duración no negativos, fecha coherente) y rechaza duplicados por id antes de persistir. La sincronización es unidireccional (push): el reloj genera la medición y la envía por /activity; la capa de datos encola el mensaje si el enlace se interrumpe y lo entrega al reconectarse, por lo que no se pierde el registro mientras el teléfono permanece vinculado. El historial local (SharedPreferences + Gson) permite auditar qué registros se aceptaron y cuáles se descartaron, cumpliendo el requisito de trazabilidad de la información sincronizada.
